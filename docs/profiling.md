# Profiling xee with samply

## Quick reference

```sh
# 1. Build with the profiling profile (optimized + debug info)
cargo build --profile release-perf

# 2. Generate dSYM bundle (REQUIRED on macOS — without this, samply shows hex addresses instead of function names)
dsymutil target/release-perf/xee

# 3. Record a profile (use ABSOLUTE path to binary)
cd xslt
samply record --save-only -o ../tmp/profile.json \
  /Users/brillo/Repositories/xee/target/release-perf/xee \
  xslt --relaxed --param paper-size=A3 --precompiled print.xeec \
  -o out.html input-small.xml

# 4. View the profile
samply load ../tmp/profile.json
# Opens Firefox Profiler at http://127.0.0.1:3000
```

## Why function names don't appear (the recurring trap)

On macOS, Rust with LTO compiles debug info (DWARF) into object files, but
the **linker does not embed it into the final binary**. Instead, the binary
contains references to the object files' locations. The `dsymutil` tool
collects that scattered DWARF info into a `.dSYM` bundle next to the binary.

Without running `dsymutil`, you get:
- `nm` shows mangled symbol names (the symbol *table* is present)
- `dwarfdump` shows empty `.debug_info` (the *debug info* is missing)
- samply/Instruments show hex addresses like `0x3c912b` instead of function names

**`debug = true` in Cargo.toml is necessary but not sufficient.** You must
also run `dsymutil` after building.

## Cargo profile setup

The `release-perf` profile in `Cargo.toml` inherits from `release` (which
has `debug = true`). No changes to Cargo.toml are needed:

```toml
[profile.release]
debug = true
lto = "thin"
codegen-units = 1

[profile.release-perf]
inherits = "release"
lto = "fat"
panic = "abort"
```

## When to re-run dsymutil

You must re-run `dsymutil target/release-perf/xee` after every rebuild of
the binary. The `.dSYM` bundle is not automatically regenerated by cargo.

A clean build (`cargo clean --profile release-perf`) removes the `.dSYM`
bundle as well.

## Inverted call tree (self-time analysis)

In Firefox Profiler, check "Invert Call Stack" to see which functions
consume the most self-time. This is the most useful view for finding
optimization targets.

If self-time is flat (no function > 1-2%), there are no single-function
bottlenecks — the workload is evenly spread across many small operations.

## Instruments (alternative)

```sh
# Record with Instruments Time Profiler
xcrun xctrace record --template 'Time Profiler' \
  --launch -- /Users/brillo/Repositories/xee/target/release-perf/xee \
  xslt --relaxed --param paper-size=A3 --precompiled print.xeec \
  -o out.html input-small.xml

# The .trace file opens in Instruments.app
```

Instruments reads dSYM bundles automatically, so you still need to run
`dsymutil` first.

## Common mistakes

| Symptom | Cause | Fix |
|---------|-------|-----|
| Hex addresses in call tree | Missing `.dSYM` bundle | Run `dsymutil target/release-perf/xee` |
| No debug info despite `debug = true` | Stale build / incremental didn't relink | `cargo clean --profile release-perf && cargo build --profile release-perf` |
| Symbols missing after `cargo build -p xee` | Only final binary was relinked, object files were cached without debug info | Full clean rebuild |
| samply can't find binary | Relative path used | Use absolute path to binary |
